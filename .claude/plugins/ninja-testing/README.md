# JavaScript Ninja — Testing Skills

Харнесс для ИИ-агентов, дистиллированный из курса «Тестирование в JavaScript» (Илья Климов, JavaScript Ninja). Плагин для Claude Code `ninja-testing` и одновременно набор скиллов по открытому стандарту [Agent Skills](https://agentskills.io) — работает в Codex, Cursor, Copilot, Gemini CLI и других агентах, читающих `AGENTS.md` и `SKILL.md`.

Идея: не существует харнесса, который подходит всем. Поведение агента зависит от модели и от проекта — одни модели тяготеют к юнитам, другие к E2E, слабым нужны перечисленные кейсы и готовая инфраструктура, сильным — нет. Поэтому здесь не один набор правил, а **генератор**: он смотрит на репозиторий, задаёт несколько вопросов и собирает харнесс под этот проект, оставляя только нужное — backend-сервис не получит правил про компонентные тесты, а frontend-приложение — про изоляцию базы данных.

## Установка

```
/plugin marketplace add xanf/javascript-ninja-testing-skills
/plugin install ninja-testing@javascript-ninja
```

Локально для разработки: `claude --plugin-dir ./javascript-ninja-testing-skills`.

Для других агентов (Codex, Cursor, Copilot…): `npx skills add xanf/javascript-ninja-testing-skills` — ставит скиллы; `AGENTS.md` и правила по директориям пишет `init`.

## Первый запуск

```
/ninja-testing:init
```

Генератор:

1. Запускает детерминированный автодетект (`scripts/detect.mjs`): runner и бандлер, фронт/бэк/fullstack, фреймворк и стор, БД/ORM/testcontainers, MSW, Playwright, Stryker, CI, структура репозитория, существующие тесты и их запахи, частота изменений файлов по git.
2. Задаёт 5–7 вопросов только о том, чего в репозитории нет: где деньги/доступ/необратимые операции, доверяете ли существующим тестам, какие внешние сервисы, параллельная ли разработка фронта и бэка, какие модели, бюджет CI.
3. Применяет правила «если-то» (`skills/init/assembly-rules.md`; по-русски и с указанием, из какого видео курса взято каждое правило — `docs/Правила сборки.md`) и показывает план: какие файлы будут созданы и какое правило это решило.
4. После подтверждения пишет в проект:

| Файл | Что это |
|---|---|
| `AGENTS.md` | ядро: 12 инвариантов курса, читается любым агентом |
| `CLAUDE.md` | `@AGENTS.md` + какие скиллы когда, какие хуки стоят |
| `.claude/rules/*.md` | path-scoped правила: юнит-тесты, бэкенд-интеграция, компонентные тесты, E2E, фикстуры — только для обнаруженных сторон |
| `.claude/agents/test-reviewer.md` | субагент механического ревью тестов в чистом контексте, желательно другой моделью |
| `.claude/hooks/ninja-testing/*.mjs` + `.claude/settings.json` | хуки: линт антипаттернов в тестах, запрет `-u`/`--no-verify`/force push, подтверждение на правку конфигов и на `Stryker disable`, требование полного прогона, а в strict — мутаций и вердикта по каждому выжившему перед завершением |
| `stryker.config.json`, npm-скрипты | `mutate` только на приоритетные файлы, `test:mutation`, `test:coverage`, `test:e2e` |

`--dry-run` — только план. `--deep` — четыре сложных решения (границы моков, стратегия изоляции БД, мутации как gate или отчёт, приоритеты legacy) анализируются всегда, а не только по триггерам.

## Два режима — одно правило

**Standard** — по умолчанию, для любой модели. **Strict** — включи, когда мутационное тестирование и самопроверка должны быть принудительными на каждой сессии: команда только начинает, тесты агента никто не читает перед мержем, или модуль про деньги/доступ. Не уверен — standard.

Standard — это контракт (`AGENTS.md`, правила по директориям), запреты (`-u`, `--no-verify`, правка конфигов ради теста), блокирующий линт тестов и требование полного прогона перед завершением; скиллы доступны по запросу, мутации обязательны перед PR. Strict добавляет пошаговые предписания скиллов в CLAUDE.md, предупреждения линта и принудительный мутационный прогон с самопроверкой на каждом Stop. Переключить — `/ninja-testing:mode strict|standard`, посмотреть — `/ninja-testing:mode status`.

Почему так, а не наоборот: на задаче с гонкой за последнее место standard ловит баг 3/3 на Haiku, 3/3 на Sonnet и 2/2 на Opus — по цене голого агента (0.2 / 0.9 / 1.7 $ за прогон); без харнесса — 0/3, 0/3, 2/2. Strict даёт тот же результат вдвое дороже (Sonnet 1.6 $, Opus 3.2 $), а на Haiku даже хуже (2/3) — пошаговые предписания отвлекают слабую модель. На задаче со Stryker Sonnet и Opus в standard сами запускают мутации и выходят на потолок 98.5 % (без харнесса 93 % и 96 %); strict там не добавляет ничего. Что strict покупает — принудительность для слабой модели: Haiku в standard запускает Stryker, пишет «тесты убивают большинство мутантов» и останавливается на 77 %; в strict Stop-хук не отпускает без вердикта по каждому выжившему — 87 % за ×3 цены. Подробности — `evals/results/СВОДКА.md`.

Две самопроверки: strict → standard, когда неделю хук ни разу не блокировал правку и ревьюер ничего не нашёл; standard → strict, когда ревьюер или Stryker нашли дыру, которую агент пропустил, а человек не заметил.

## Что набирает человек — три команды

| Команда | Когда |
|---|---|
| `/ninja-testing:init` | один раз на репозиторий: автодетект, вопросы, харнесс |
| `/ninja-testing:review` | перед мержем тестов: механику проверяет субагент `test-reviewer` в чистом контексте, человеку остаётся вопрос «каких тестов не хватает» |
| `/ninja-testing:mode` | переключить standard ↔ strict, посмотреть правило выбора |

Больше человеку помнить нечего: остальное агент делает сам, по контракту и по ситуации. Формулируйте задачу по-человечески — «покрой фичу X тестами», «реализуй по этому ТЗ», «тест прошёл после ретрая, разберись» — и агент возьмёт нужную процедуру.

## Что знает агент — восемь процедур

Скрыты из слэш-меню (`user-invocable: false`), вызываются моделью по описанию; в strict-режиме CLAUDE.md предписывает их явно.

| Процедура | Агент берёт, когда | Из курса |
|---|---|---|
| `test-as-spec` | реализует функцию по задаче — сначала таблица вход→выход с границами | 3.1, 5.5, практики 1–2 |
| `test-plan-by-level` | «покрой фичу тестами» — план по уровням до первого теста | 4.1, 4.4, практика 3 |
| `mutation-loop` | написал/поменял тесты на логику — Stryker до PR, вердикт по каждому выжившему | 2.5, 5.5, практики 1 и 4 |
| `legacy-characterize` | меняет код без тестов: разведка → пиннинг → рефакторинг → тесты | 5.4, практика 4 |
| `integration-boundaries` | пишет интеграционный тест: что внутри слайса, что сосед, что внешнее | 4.2–4.4, практика 3 |
| `external-contract` | нужен фейк внешнего сервиса или контракт фронт/бэк | 4.5, 3.3, практика 3 |
| `e2e-select` | просят E2E или «покрой критичные пути» — три критерия | 5.1, 5.3, практика 4 |
| `flaky-triage` | тест прошёл после ретрая: диагноз, запреты, карантин | 5.3, 2.3, практики 1 и 4 |

В других агентах (Codex, Cursor, Copilot) разницы нет: там скиллы и так подхватываются по описанию в `SKILL.md`.

## Что внутри правил

Двенадцать инвариантов ядра (`templates/AGENTS.md`): поведение, а не реализация; тест как ТЗ для агента; честный тест (без логики, название ↔ expect, AAA); юнит быстрый, изолированный, детерминированный; дублёры по вопросу «вызов или результат»; фикстура — фабрика; уровень теста по вопросу «что должно сломаться»; граница мока там, где кончается своё; три критерия E2E; мутационное тестирование как шаг верификации; ревью = механика + суждение; метрики — три вместе и никогда как цель.

Откуда каждая формулировка — в `docs/Голос курса.md` (цитаты из записей по темам) и в колонке «Из курса» выше. Сами скиллы, правила и сообщения хуков на курс не ссылаются: агент читает их в чужом репозитории, где никакого «видео 4.2» нет, и они должны стоять сами по себе.

## Структура репозитория

```
.claude-plugin/       plugin.json, marketplace.json
skills/               3 команды (init, review, mode) + 8 процедур агента (SKILL.md, reference.md)
agents/               test-reviewer.md
scripts/detect.mjs    автодетект репозитория
scripts/hooks/        test-lint.mjs, guard.mjs, stop-check.mjs (копируются в проект при init); selftest.sh — 32 проверки хуков
templates/            AGENTS.md, CLAUDE.md, rules/*.md, settings.json
docs/                 Правила сборки, Голос курса, Компаньоны, SKILL-STYLE
```

Плагин сам не устанавливает глобальных хуков — они появляются только в репозитории, где запущен `init`, и живут в нём независимо от плагина. В git worktree хуки работают с деревом, в котором находится агент (`git rev-parse --show-toplevel` от текущего `cwd`): правки и прогоны из основного дерева не засчитываются, а `.claude/ninja-testing.json` берётся из worktree, если он там есть, иначе из основного дерева.
