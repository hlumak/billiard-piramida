# Правила сборки харнесса

Команда `/ninja-testing:init` не копирует в проект один и тот же набор файлов. Она работает в шесть шагов: сначала скрипт `detect.mjs` детерминированно собирает факты о репозитории (раннер, фреймворк, база, наличие тестов и их «запахи», история изменений в git); затем задаёт короткий опрос — только о том, чего по коду не понять; затем применяет правила вида «если факт — то файл или строка»; для четырёх решений, где простого «если-то» не хватает, проводит анализ и просит вас подтвердить гипотезу; после этого показывает план — список файлов с указанием, какое правило каждый из них породило — и только после вашего согласия пишет файлы. Так бэкенд-сервис не получает правил про компонентные тесты, а фронтенд-приложение — правил про изоляцию базы данных.

Обещание генератора: у каждой сгенерированной строки есть идентификатор правила (A-CORE, C-DB-2, D3 и т. д.) и ссылка на источник в курсе — номер видео или практики. Этот документ — расшифровка этих идентификаторов: зачем правило существует, при каком условии срабатывает и откуда в курсе оно взялось. Идентификаторы совпадают с теми, что печатаются в плане и в итоговой сводке.

## Что определяется автоматически

`detect.mjs` читает `package.json` всех пакетов, конфиги и историю git. Ничего не спрашивает и ничего не меняет.

| Группа фактов | Что именно смотрит | Что из этого следует |
|---|---|---|
| Раннер и бандлер | Vitest / Jest / Rstest / Mocha / `node --test`; vite / rspack / webpack / esbuild / next; конфиг-файлы | Выбор команд запуска, рекомендация о миграции с Jest |
| Режим окружения | `environment: jsdom/happy-dom` в конфиге, `@vitest/browser`, `vitest-browser-*` | Сигнал `frontend:jsdom` — рекомендация перейти в Browser Mode |
| Покрытие, property-based | `@vitest/coverage-*`, скрипт с `coverage`, `fast-check` | Добавить `test:coverage`, предложить `fast-check` |
| Фронтенд | React / Vue / Angular / Svelte / Solid; стор (zustand, pinia, redux, mobx, ngrx, jotai); Testing Library, Vue Test Utils, Storybook, i18n | Какой пакет Browser Mode ставить, как называть стор в правиле |
| Бэкенд | express / fastify / nest / hono / koa; ORM (drizzle, prisma, knex, typeorm, sequelize, mongoose, kysely); БД (postgres / mysql / sqlite / mongo); redis; testcontainers / PGlite; supertest; docker-compose; DI-контейнер; Effect | Какие правила про интеграцию и изоляцию БД писать |
| Дубли и контракты | MSW, sinon, nock, axios и axios-mock-adapter, zod, Effect Schema, файлы OpenAPI | Механизм подмены зависимостей, «бухгалтер» необработанных запросов |
| E2E | `@playwright/test`, cypress, папка `e2e/` и конфиг | Писать ли правило `e2e.md`, какой инструмент называть |
| Мутационное тестирование | `@stryker-mutator/core`, конфиг, npm-скрипт | Предлагать Stryker или проверять существующий конфиг |
| CI | `.github/workflows`, `.gitlab-ci.yml`, `.circleci`, Jenkinsfile и др.; husky / lefthook | Рекомендация «настрой CI», формулировки про pre-commit |
| Структура | Монорепозиторий (workspaces, pnpm, turbo, nx); FSD-подобные папки (`features`, `entities`, …); `modules` / `domains` / `slices`; тесты рядом или в `tests/`; TypeScript | Пути в правилах, нужен ли анализ границ моков (D1) |
| Существующие тесты | Количество, примеры, интеграционные и characterization-тесты; использование `getByTestId`, `querySelector`, снапшотов, подмены `fetch`, объектных фикстур, `toHaveBeenCalled`, MSW | «Известный долг» в CLAUDE.md, что хуки будут запрещать в новых тестах |
| История git | Число коммитов за 12 месяцев; 25 самых часто меняемых файлов и есть ли у них тест (`hotFiles`, `hotUntested`) | Подсказка для вопроса о критичных местах, вход для приоритизации legacy (D4) |

Стороны проекта (`sides`) выводятся из этих фактов: фронтенд — если найден фреймворк, Testing Library или Browser Mode; бэкенд — если найден серверный фреймворк, ORM, БД или supertest. Если найдено и то и другое, но нет монорепозитория или явных папок `client`/`server`, генератор считает, что не уверен, и задаёт первый вопрос опроса.

Сигналы, которые заставляют генератор задать вопрос или предложить решение: `sides:unknown`, `runner:jest-with-bundler`, `frontend:jsdom`, `frontend:rtl-no-browser-mode`, `backend:db-without-test-db`, `backend:cache-shared-resource`, `network:no-msw`, `network:axios-no-msw`, `mutation:no-stryker`, `ci:none`, `tests:none`, `tests:hot-untested-files`, `tests:snapshots-present`, `tests:testid-or-css-locators`, `tests:fetch-mocked`, `tests:object-fixtures`, `structure:slices-not-explicit`, `doubles:di-framework`, `doubles:effect`.

## Вопросы опроса

Вопросы задаются по одному, рекомендуемый ответ — первым. Если факт уже известен, вопрос пропускается с пояснением в одну строку («БД не обнаружена — вопросы про изоляцию пропускаю»).

| № | Вопрос | На что влияет |
|---|---|---|
| 1 | Стороны: backend, frontend или fullstack? (только если детектор не уверен) | Какие наборы правил вообще существуют в проекте (B-BE, B-FE) |
| 2 | Критичные места: где деньги, доступ и необратимые операции — платежи, выдача прав, письма, удаление данных. Подсказка — часто меняемые файлы без тестов | Приоритетные модули: что мутировать (C-MUT-1), какие E2E нужны (B-E2E, C-E2E-3), с чего начинать в legacy (D4) |
| 3 | Стадия: (a) проект новый; (b) тесты есть, доверяю; (c) тесты есть, качество разное — назвать 2–3 образцовых файла; (d) legacy без тестов | Раздел «Где начинать» в CLAUDE.md, белый список образцов, порядок шагов (C-ST-1…4, C-E2E-5) |
| 4 | Внешние сервисы, которые команда не контролирует; есть ли для них OpenAPI/типы. Сервисы соседних команд — свои или внешние? | Список внешних границ и контракт-проверка (C-EXT-1, C-EXT-3, C-DB-6) |
| 5 | Фронт и бэк делают параллельно разные люди или агенты? | Обязательная схема контракта до начала работы (C-EXT-2) |
| 6 | Модели: основная; есть ли вторая для ревью; будут ли слабые/локальные модели писать код? | Модель ревьюера (C-MD-1/2), режим `it.todo` и явные списки кейсов (C-MD-3, C-MUT-4) |
| 7 | CI: есть ли; сколько минут допустимо на пайплайн MR; есть ли ресурсы для мутационного тестирования в CI. Доступен ли Docker разработчикам и в CI (если найдена БД без тестового инструмента) | Порядок и объём прогонов (C-CI-1…4), выбор тестовой БД (C-DB-1/2), gate или отчёт для Stryker (D3) |
| доп. | Есть ли долгие сценарные тесты (feature specs), для которых строгий Arrange-Act-Assert неудобен? | Исключение из правила AAA (C-MD-4) |

## Правила

Правила с одним фактором — обычное «если-то». Правила, помеченные как D1–D4, требуют анализа и описаны в отдельном разделе ниже.

### A. Всегда

| id | Что делает | Откуда в курсе |
|---|---|---|
| A-CORE | Пишет `AGENTS.md` из шаблона и `CLAUDE.md`, который подключает его через `@AGENTS.md` | Видео 1.1–1.5, 3.1, 5.2, 5.5; практика 2: базовые правила — в CLAUDE.md, скиллы — когда инструкции огромные |
| A-UNIT | Пишет `.claude/rules/unit-tests.md` | Видео 3.2, 3.3, 3.5; практики 1 и 2: unit-тест проверяет поведение, а не реализацию |
| A-FIXT | Пишет `.claude/rules/fixtures.md` | Видео 2.2; практика 1, этап 6: фабрики вместо объектов-фикстур |
| A-HOOKS | Устанавливает три хука (`test-lint`, `guard`, `stop-check`) и сливает `settings.json` | Видео 2.3, 2.4, 3.5, 5.3; практика 1: агент «стреляет из пушки по воробьям» — хук ловит это раньше человека |
| A-REVIEWER | Устанавливает субагента `test-reviewer` | Видео 5.2; практика 3: ревью идёт по цепочке description → expect → что замокано → логика |
| A-CI | Если CI нет — первая рекомендация в сводке: «настрой CI, даже в одиночку». Хуки не замена: агент может обойти локальный хук | Видео 2.4 |
| A-FULLRUN | Stop-хук требует полный параллельный прогон, если менялись тесты или логика | Видео 2.3, 2.4 |

### B. Стороны — что остаётся, что выбрасывается

| id | Условие | Что делает | Откуда в курсе |
|---|---|---|---|
| B-BE | Найден бэкенд | Пишет `integration-backend.md`; `{{BACKEND_PATHS}}` — серверные папки (`packages/server/**`, `apps/api/**`, `src/server/**` или `src/**` без монорепозитория) | Видео 4.2, 4.4; практика 3, модуль 2: интеграционный тест бэкенда идёт через реальную БД |
| B-FE | Найден фронтенд | Пишет `component-tests.md`; `{{FRONTEND_PATHS}}` — клиентские папки и тесты `*.{tsx,jsx,vue,svelte}`; добавляет скрипт `test:browser` | Видео 4.3; практика 2, этап 4: компоненты тестируются в реальном браузере |
| B-E2E | Playwright или Cypress в зависимостях, либо названы критичные сценарии | Пишет `e2e.md`; `{{E2E_PATHS}}` — `e2e/**`, `**/*.e2e.*`, папка из конфига Playwright | Видео 5.1, 5.3; практика 4: E2E — только на критичных путях |
| B-NO-FE | Фронтенда нет | Не пишет `component-tests.md`, скрипт Browser Mode и заметки про MSW в браузере; предупреждения хуков о локаторах молчат сами (они смотрят на содержимое файла) | — |
| B-NO-BE | Бэкенда нет | Не пишет `integration-backend.md`, изоляцию БД, testcontainers, `committedDb` | — |
| B-SHARED | Монорепозиторий с пакетом `shared`/`common`, где лежит чистая логика | Заметка в CLAUDE.md: «чистая бизнес-логика, общая для двух сторон, живёт в `<shared>` и покрывается unit-тестами один раз там» | Практики 2 и 3, обзор проекта |

## Четыре решения, где «если-то» не хватает

Каждое из них — анализ → гипотеза → подтверждение. Генератор никогда не принимает их молча. В режиме по умолчанию они запускаются только по сигналу; в режиме `--deep` — всегда.

### D1 — Границы моков (видео 4.4)

- **Когда:** сигнал `structure:slices-not-explicit` при наличии бэкенда — папки не говорят, где проходят границы модулей.
- **Факторы:** приоритетные модули из вопроса 2 и граф их импортов (`grep -rn "from '" <модуль>`).
- **Анализ:** каждый импорт классифицируется. Та же папка или фича — *внутри слайса*: не мокается никогда, включая базу. Другая фича — *сосед*: можно замокать модуль, но не его таблицы. Пакет из `node_modules`, который ходит в сеть или сервис не нашей команды — *внешний*: fake на уровне сети плюс контракт.
- **Что подтверждает человек:** если структура FSD-подобная или есть `modules/`, разметка выводится из папок и лишь подтверждается; иначе показывается таблица, и вы её правите.
- **Куда пишется:** таблица «Slices in this repo» в конец `integration-backend.md` (и в `component-tests.md` для фронтенд-слайсов).

### D2 — Стратегия изоляции БД (видео 2.3, 4.2; практика 3)

- **Когда:** найдена любая база данных.
- **Факторы:** (a) параллельные воркеры — `pool`, `fileParallelism` в конфиге раннера, ядра в CI; (b) поддерживаются ли вложенные транзакции и не открывает ли код свои транзакции конфликтующим образом (Postgres и SQLite — savepoint работает; MySQL — ограниченно; Prisma — оговорка про интерактивный `$transaction`); (c) есть ли кэш перед базой; (d) есть ли сценарии с конкуренцией — лимиты, балансы, блокировки (вопрос вам).
- **Анализ и решение:** без параллелизма — откат транзакции на каждый тест; параллелизм и (b) в порядке — откат транзакции плюс своя БД или схема на воркер; (b) не в порядке — reset + seed на каждый тест; (c) — flush кэша на тест или пространство ключей на воркер; (d) — дополнительно `committedDb`, второй клиент без обёртывающей транзакции, для тестов конкуренции.
- **Что подтверждает человек:** предложенную стратегию и ответ про конкуренцию.
- **Куда пишется:** `{{ISOLATION_STRATEGY}}` и `{{COMMITTED_DB}}` в `integration-backend.md`.

### D3 — Мутационное тестирование: gate или отчёт (видео 2.5, 5.6; практика 4)

- **Когда:** Stryker уже есть или его добавляют.
- **Факторы:** время полного unit-прогона `t` (измеряется командой `time`), число файлов-кандидатов `n` (чистая логика в приоритетных модулях), бюджет CI из вопроса 7.
- **Анализ:** стоимость одного прогона ≈ `t × 30…100`; при ограничении на изменённые файлы — намного меньше. Бюджет позволяет и инкрементальные/ограниченные прогоны Stryker укладываются — **жёсткий gate на каждый MR** (`thresholds.break` = 90 для начала, потом по доменам). Бюджет тесный — **только отчёт** в CI плюс напоминание Stop-хука локально (`ninja-testing.json: mutation.required = true`). CI нет — только локально, `mutation.required = true`. Никогда 100. Никогда на E2E; на интеграционных — только если они быстрые.
- **Что подтверждает человек:** выбранный режим и порог.
- **Куда пишется:** `stryker.config.json` (значение `break` появляется только при выборе gate) и `.claude/ninja-testing.json`.

### D4 — Приоритеты в legacy (видео 5.4; практика 4)

- **Когда:** стадия (d) или сигнал `tests:hot-untested-files`.
- **Факторы:** таблица по файлам — число изменений за 12 месяцев (`git.hotFiles`), инциденты (вы берёте из трекера или агент сканирует последние ~100 багов), столбец «деньги / доступ / необратимость» (заполняете вы).
- **Анализ:** сортировка — сначала инциденты, потом деньги, потом частота изменений: «где ломается, где часто трогают и где деньги».
- **Что подтверждает человек:** итоговые 2–3 модуля.
- **Куда пишется:** раздел «Где начинать» в CLAUDE.md; первый шаг для каждого модуля — `legacy-characterize`. Рядом напоминание: pinning-тесты строго до рефакторинга; одна «ручка» за раз; в остальном коде — правило бойскаута.

## Чего генератор никогда не делает

- Не пишет правила для стороны, которой в проекте нет.
- Не ставит `mutate: ["src/**"]` — мутируются только файлы чистой логики в приоритетных модулях.
- Не ставит мутационный порог 100 и не делает gate только по покрытию.
- Не вносит в кодовую базу DI, порты или адаптеры — механизм подмены берётся тот, что уже есть.
- Не добавляет соглашений про `data-testid`.
- Не перезаписывает ваш текст в существующих файлах инструкций, не показав diff.

## Как перезапустить

- `/ninja-testing:init --dry-run` — только план и предпросмотр файлов, ничего не записывается. Удобно, чтобы посмотреть, какие правила сработают, до любых изменений.
- `/ninja-testing:init --deep` — помимо семи вопросов проводятся все четыре анализа D1–D4, а не только те, что вызваны сигналами.
- `--lang ru|en` — язык общения в опросе и сводке; сгенерированные файлы всегда на английском.
- Если `AGENTS.md`, `CLAUDE.md`, `.claude/rules/`, `.claude/settings.json` или `.claude/agents/test-reviewer.md` уже существуют, генератор их читает и **сливает**, а не заменяет: ваш текст сохраняется, добавляется секция с меткой `<!-- ninja-testing -->`, массивы в `settings.json` объединяются, а diff показывается до записи.
- После записи генератор запускает `test-lint.mjs` с пустым вводом и, если добавлял Stryker, `npx stryker run --dryRunOnly` — пока это не выполнено, он не утверждает, что хуки и Stryker работают.
