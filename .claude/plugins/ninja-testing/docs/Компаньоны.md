# Компаньоны — сторонние скиллы, которые можно поставить рядом

Харнесс `ninja-testing` самодостаточен: всё, что нужно для курса, написано своими словами. Ниже — чужие скиллы, которые полезны как справочники по API конкретных инструментов, и оговорки, где они расходятся с курсом. Ставить их не обязательно; если ставите — правила курса имеют приоритет (они в `AGENTS.md`, и хуки их защищают).

| Скилл | Что даёт | Где расходится с курсом | Установка |
|---|---|---|---|
| [anivar/msw-skill](https://github.com/anivar/msw-skill) | 20 правил по MSW: `setupServer`/`setupWorker`, `server.use` на тест, `resetHandlers`, `onUnhandledRequest: 'error'` («то, что агенты чаще всего пропускают») | не расходится; добавьте абзац про `setupWorker` в Vitest Browser Mode | `npx skills add anivar/msw-skill` |
| [antfu/skills → vitest](https://github.com/antfu/skills/blob/main/skills/vitest/SKILL.md) | справочник по API Vitest 5, сгенерированный из документации (Anthony Fu, Vitest core) | без мнений; про Browser Mode ничего нет, снапшоты описаны нейтрально — наш `component-tests.md` и правило «избегать snapshot» главнее | `pnpx skills add antfu/skills --skill vitest` |

| [citypaul/.dotfiles → react-testing, front-end-testing](https://github.com/citypaul/.dotfiles) | Vitest Browser Mode + `vitest-browser-react`, `expect.element`, MSW `setupWorker`, порядок локаторов role → label → text | `front-end-testing` допускает jsdom для «чистой логики без браузера» — курс: jsdom только если браузерный прогон > ~15 с; соседний `testing`-скилл предпочитает DI вместо module mocking — курс: `vi.mock` по умолчанию | `npx skills add citypaul/.dotfiles --skill react-testing` |

| [mattpocock/skills → grill-me](https://github.com/mattpocock/skills/blob/main/skills/productivity/grill-me/SKILL.md) | «допрос» по дереву решений до исчерпания развилок — тот приём, который в курсе назван как Deep Interview / GrillMe (видео 3.1) | не расходится; курс предпочитает «меньше вопросов в процессе + список решений в конце» — используйте до `test-as-spec`, когда задача действительно неоднозначна | `npx skills@latest add mattpocock/skills` |

## Чего ставить не стоит

- **superpowers `test-driven-development`** и **mattpocock `tdd`/`mocking.md`** — оба продвигают DI вместо module mocking и «без моков, если не неизбежно»; это прямой конфликт с видео 3.4 («не вводите DI ради тестов, если реализация одна»). Цикл red→green сам по себе не противоречит, но сопутствующие правила про моки будут спорить с `AGENTS.md`.
- **microsoft `playwright-component-testing`** — конкурирует с Vitest Browser Mode за компонентный слой; в курсе компонентные тесты — в Browser Mode, Playwright — только E2E.
- **testcontainers/claude-skills** — только Go и .NET; для Node ничего нет, поэтому наш `integration-backend.md` и `integration-boundaries/reference.md` описывают testcontainers-node сами.

## Официальные инструменты Claude Code, которые дополняют харнесс

- `/init` с `CLAUDE_CODE_NEW_INIT=1` — интерактивный генератор CLAUDE.md, читает `AGENTS.md`; запускайте **после** `/ninja-testing:init`, чтобы он подхватил тестовый слой, а не написал свой.
- `/import` — разовый импорт AGENTS.md и чужих конфигов в CLAUDE.md, если проект уже жил под другим агентом.
- `.claude/rules/*.md` с `paths:` — механизм, на котором стоят наши path-scoped правила; в него же кладите свои доменные правила (например, «в этой директории учитывай race conditions» — практика 3).
